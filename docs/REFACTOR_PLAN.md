# Implementation plan after Phase 01

**Proposal for owner approval · 19 November 2026.** Start with the posting and authorization boundaries. A correct calculation on incomplete or duplicated entries produces an incorrect report. Keep the application as a single React client with PostgreSQL posting rules and a small set of explicit client services.

Finding IDs (A) are in [CORE_AUDIT.md](CORE_AUDIT.md). Owner decisions (B) and the acceptance ledger are in [BUSINESS_RULES.md](BUSINESS_RULES.md). Task IDs below identify ordered work packages. Each numbered slice is a separately reviewable change with its own stop condition. **Change risk** estimates the cost of a mistaken implementation: high affects persisted money, access or recovery, medium affects reported results or user workflows, low affects tests or internal structure. Finding severity measures the current problem separately.

**Release sequence.** Phase 1 can begin with local characterization. Treat unresolved A01 as a release gate. Ship posting, access, read coverage and UI corrections in separate, reviewable deliveries. Changes to historical records, live permissions, SQL or restore procedures require their own approval, isolated rehearsal and compatible recovery point. A screen or adapter change can be reverted independently. Once money has posted, use reconciliation and approved compensating entries to correct it. Restoring an older client must not cause it to replay already-confirmed work.

**Optional enhancements.** If the owner needs an as-of balance statement, build it from dated signed movements after the cutover contract is established. If browser memory becomes a measured constraint, add one scoped server aggregate for the affected report. Neither improvement is a prerequisite for the core corrections.
