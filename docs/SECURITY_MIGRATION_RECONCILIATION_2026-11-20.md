## Reproduced defects and change

With the new migration empty, the full-schema regression reproduced three defects: `ensure_my_profile()` rewrote a demoted user's legacy `shop_members.role` from the stale profile; the privileged `post_transaction_draft()` could post for an enrolled AAL1 user; and authenticated users retained table-level UPDATE on all payment account balance columns despite an earlier column-level REVOKE. Existing #26 tests used a reduced schema and missed these paths. The full-schema cross-tenant retry and inactive membership checks already passed.

The new migration makes the transaction UPDATE policy use canonical active membership, synchronizes the legacy role mirror from that same membership, and checks MFA assurance before the privileged draft RPC reads either a draft or an idempotent receipt. It removes broad payment account UPDATE and grants only metadata columns to authenticated owners. Posting triggers and definer functions retain their account update privileges. Existing customer balances and postings remain untouched.

## Remaining release risks

1. PGlite does not reproduce the complete Supabase Auth/PostgREST/MFA service stack, separate database connections, provider roles, or real delivery order metadata. No isolated hosted staging branch exists. Test owner/manager/cashier/inactive/demoted users, cross-company draft guessing and retries, enrolled/un-enrolled MFA, and account writes on a disposable Supabase project restored from a sanitized schema. Rehearse backup and rollback before approval.
2. The older `syncEngine` still queues `payment_accounts` UPSERTs containing `current_balance` and `opening_balance`. Broad UPDATE removal deliberately blocks those cloud updates; a conflict will stay in the local queue and eventually be marked failed. Reconcile historical local account balances and route new financial movements through the authoritative posting path before deployment. Never discard the pending local entries or convert them into invented journals.
3. `INSERT` on `payment_accounts` still accepts owner-entered opening balances because that is an existing workflow. Define and approve opening-balance policy, source evidence and V2 cutover separately. Direct ordinary-user UPDATE is blocked; a privileged key or incorrectly exposed definer remains outside this test's guarantee.
4. The app currently chooses one active company through `get_auth_org_id()`. True multi-company switching, V2 Chart of Accounts, immutable balanced journals, fiscal periods, approval audit and reversal controls still require their planned, separate accounting PRs. Do not enable V2 posting from this migration alone.
5. Check all existing definer functions, grants, views, MFA policies and role mirrors on the effective staging schema. Historical migration filenames are not evidence of their deployed order or definition. Do not merge #26 and this PR merely because PGlite passes.
