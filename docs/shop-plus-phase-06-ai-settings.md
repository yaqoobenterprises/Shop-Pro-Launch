# Shop Plus — Phase 06: LedgerMate AI, Settings and security surfaces

## LedgerMate AI
- Neutral Ledger Ink surfaces, compact header/composer, clear AI-service availability instead of model identifier, keyboard-accessible history, descriptive empty state, English and Roman Urdu suggestions, reduced motion and semantic Markdown tables.
- Default read-only. Eligible owner/manager cloud users (PKR) can explicitly enable reviewed ledger actions for the current mounted workspace. Existing deterministic preparation, preview, permission checks, confirmation and draft retry retained. Demo/non-PKR actions disabled; no model tool or unrestricted database access. Clear/new/switch controls cannot discard a submitted pending action inside LedgerMate; navigation away can still unmount it. Full persisted action recovery is a release gate.
- Exact supported daily income, month-to-date cashbook results and current cash/bank questions use direct authorized cloud reads and BigInt calculations, bypassing model arithmetic; dates, record counts, source scope, currency and where to verify are included. Other questions use existing context/date resolver and AI streaming. Context omits free-form notes/raw transaction descriptions, includes record IDs for detail requests, validates integer amounts, avoids inherited dates and financial reads for greetings/unrelated/concept-only messages, and uses configured currency. Current AI health gate is retained, including for direct answers. The supported direct-query grammar is deliberately narrow; general language remains model-assisted and can be wrong.
- Abortable provider fetch with timeout; discard partial response on stop/failure, retain complete previous answer during regeneration, retry last question, avoid forcing scroll while user reads earlier messages. Incomplete streaming messages are excluded from local persisted history. Remote history reconciliation architecture and retention remain unchanged; stop does not cancel already completed provider work or in-flight ledger reads, and no mutation is canceled by the Stop response control.
- Existing server verifies the caller's session and keeps provider key server-side. Client-supplied context is explicitly untrusted, placed in a non-system message, never represented as independently authenticated by endpoint. No free-form notes sent through the context builder. Prompt injection cannot be eliminated by instructions alone; category/account labels and past chat remain untrusted. Live provider integration, rate limiting, data-sharing/privacy review, independently authenticated server-side retrieval and comprehensive security testing remain release gates.

## Settings and remaining screens
- Responsive settings navigation and panels, consistent auth shell styling; existing feature flags and settings visibility preserved. Profile save/photo, password and MFA actions have synchronous duplicate-request guards. No auth/session or MFA policy changes.
- Category edits, additions, archive and restore gated by existing business-management permission and successful cloud session. Require a returned row before reporting success. Always archive instead of deleting even unused categories. Existing category IDs/types and transactions retained; renames explicitly change displayed labels in reports.
- Transaction exports use existing paginated strict-cloud query and include active and voided records; distinguish cloud export from local recovery file. CSV escapes potentially executable formula text, and download object URLs revoked. Owner-only recovery guarded against concurrent operations and oversized input, demo mutations disabled. Existing validated recovery format and restore service unchanged; actual restore not performed.
- Currency changes fail closed on missing counts, transactions, ledger records, drafts, transfers, nonzero opening/current balances, and local pending transactions, drafts or account operations. Recheck before writing and verify returned row. No conversion/reclassification. This client-side check cannot guarantee atomicity against concurrent activity on another device; deployed database currency constraints must be reviewed. New-shop setup remains subject to existing feature flags.
- Remaining auth/recovery and unauthorized-state visual/manual testing, full data protection review, server authorization verification, and live persistence remain outstanding.
