# Shop Pro V2 engineering and business logic audit

**19 November 2026 · `codex/shop-pro-core-audit` · `4f730ebffea2e5ec91e1586c0c6cc65b7083be80`**

**Release assessment.** A confirmed expense can reach a different book depending on which button the operator uses. A single draft can also produce two postings after an ambiguous network response. These are higher priorities than splitting large components. The recorded tenant-authorization release blocker also needs a current schema comparison. This review found no evidence about how many real shops or entries have been affected.

Use the [business rules](BUSINESS_RULES.md) for the calculation contract and owner decisions, the [glossary](DOMAIN_GLOSSARY.md) for proposed names, and the [refactor plan](REFACTOR_PLAN.md) for dependencies, change risk and acceptance tests.

## Architecture and storage

| Area | Implementation and boundary |
| --- | --- |
| Workspace | `src/main.tsx` and `src/App.tsx` compose a React/TypeScript Vite PWA. `MainShell` selects Cashbook, LedgerMate, Overview, transaction explorer, reports, accounts and settings. `public/sw.js` caches same-origin assets for offline use. The reference app under `design-reference/` has its own manifest and lockfile. |
| Identity | `src/context/AuthContext.tsx` coordinates cloud sign-in, profile provisioning, MFA, device PIN, cached local identities and demo. `src/lib/security.ts` holds the current principal. `src/lib/supabase.ts` checks for a matching cloud session. | Entry | `src/parser/{normalizer,matcher,classifier}.ts` proposes a type, amount, date and category. `ConfirmationModal.tsx` validates the reviewed fields. `ChatView.executeSave` saves a draft then selects a payment account for posting. `AppContext.tsx` owns shortcuts, dialogs and refresh state. | Financial storage | A shop owns payment accounts, categories, transactions and transfers. Drafts are unposted. Posted transactions have a positive amount, a business date, an account and optionally a category. Composite foreign keys tie transaction account/category and draft category to their shop. Signed movements in `account_ledger_entries` and a cached balance in `payment_accounts` are maintained by triggers. `audit_log` records old/new transaction updates. |
| Reads | Day Overview reads SQL views and sometimes overlays a local queue. Other periods and Reports page through active transactions and aggregate in TypeScript. ## Verification priorities

- **Protect working controls.** The posting RPC locks the draft, validates the selected shop account, inserts and deletes atomically, and uses a unique key. The movement trigger updates balances by signed delta in SQL. Transfers lock accounts in ID order. Transaction edits/voids/restores include shop, status and `updated_at` predicates and check the returned row. The service requires a connection for these corrections. Keep these properties in acceptance tests.
- **Test at the real boundary.** `tests/pglite_database.test.ts` covers mixed entries, reversals, cross-shop category references and role restrictions with selected archived migrations. `tests/reports_sample_month.test.ts` uses a hand-calculated month on the archived foundation. `tests/launch_authorization_migration.test.ts` constructs a reduced schema for the hardening SQL. `tests/security_migrations.test.ts` uses an MFA probe. These are valuable targeted tests. Add an ordered active-schema check and full UI-to-posting-to-report cases in an approved implementation phase.
- **Separate truth from presentation.** `ledgerReadPolicy.requireAuthoritativeCloudRead` already supports exact-source reads. Preserve the matching-session check, explicit user confirmation for LedgerMate actions, server-only model key and per-user chat ownership. Verify row policies together with effective grants and the execution role of privileged functions. [Supabase RLS guidance](https://supabase.com/docs/guides/database/postgres/row-level-security)
- **Keep performance work proportionate.** Daily reads can hit a row cap, and `getAccountLedger` explicitly returns the latest 100 movements. All-history exports and some LedgerMate category queries fetch every matching page into browser memory. Treat the latter as a volume risk. Measure representative shop histories before adding aggregation infrastructure or indexes. Existing account/date and shop/date indexes provide a starting point.
